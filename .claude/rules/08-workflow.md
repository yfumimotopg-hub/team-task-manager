# 08. Claude Code の作業手順

## 標準フロー

### 1. 理解

- タスクを自分の言葉で言語化する。
- 関連する `.claude/rules/*`・既存コード・関連する `docs/adr/*` を読む。
- 既存のユーティリティ・パターンを探す（[02-coding-standards.md](02-coding-standards.md)）。

### 2. 計画

- 影響範囲を洗い出す（frontend / backend / db / api / test）。
- 変更方針を短く提示する。

### 3. 確認の要否を判断する

**着手前に人間へ確認する:**

- 仕様の重大な曖昧さ
- セキュリティに関わる変更（認証・認可・セッション・トークン・個人情報）
- API / DB / 公開挙動の破壊的変更
- アーキテクチャの変更（レイヤ構成・依存方向・ディレクトリ規約・主要ライブラリ）
- 未決定の重要な技術選択（本来 ADR で決めるべきもの）
- [09-guardrails.md](09-guardrails.md) に該当するもの

**自律的に進める:**

- 上記に当たらない軽微な実装判断。
- 既存パターン・命名・近傍のコードに合わせることを優先し、後で差分で説明できる状態にする。
- 迷ったら止めて確認する。ただし軽微な判断まで逐一止めない。

### 3-1. 既存パターンがまだ存在しない初回実装

このプロジェクトは初期段階であり、最初の実装では参照できる既存パターンがない。

- **既存パターンが存在する場合は、それを最優先する。**
- **既存パターンがまだ存在しない最初の実装では、次の順で判断する:**
  1. Rule（`.claude/rules/*`）
  2. 関連する ADR（`docs/adr/*`）
  3. 使用ライブラリの公式推奨パターン
- **最初の実装で確立したパターンは、その後の実装で一貫して再利用する。**
- ただし重要な技術選択（[09-guardrails.md](09-guardrails.md) 該当）に当たる場合は、
  既存パターンがなくても勝手に決めず、ADR / ユーザー確認を行う。

### 4. 実装

- 小さいステップで進める。バックエンドはレイヤ順で:
  `model / schema → repository → service → router` → その後フロント `features/*/api → hooks → UI`。
- 一度に触るファイル数を絞る。**無関係な広域リファクタを混ぜない。**

### 5. テスト

- 対応するテストを同時に追加・更新する。
- 変更に関連するテスト・利用可能な型チェック・lint を実行する（[06-testing.md](06-testing.md)）。

### 6. セルフレビュー

- 差分を確認する。
- [09-guardrails.md](09-guardrails.md) と照合する。
- テスト / 型チェック / lint の結果を確認する。

### 7. 報告

- 変更点・実行したチェックと結果・レビュー観点・残課題を要約する。
- **失敗や未実施は隠さず明示する。**

### 8. コミット

- ブランチ上でコミットする（[07-git.md](07-git.md)）。
- `push` / PR はユーザーの指示を待つ。

### 9. スコープ管理

- スコープ外の改善は勝手に実施せず、別タスクとして提案する。
- 重要な設計判断には ADR ドラフトを添える。

## ADR の扱い

- 重要な技術判断は `docs/adr/NNNN-title.md` に記録する。
- 未決定の事項は「未決定」と明示する。暫定選択には **理由** と **再検討条件** を書く。
- Rule で未決定としている事項（[01-architecture.md](01-architecture.md) / [04-backend.md](04-backend.md) / [05-database.md](05-database.md) / [06-testing.md](06-testing.md) 参照）を勝手に確定しない。
